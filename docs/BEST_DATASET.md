# BestDataset

Start **Build / renew BestDataset** on the profile files screen after explicit batch import. This queues a local job; import alone never starts a renewal. The same workflow is declared in the catalog for GUI, CLI and MCP. A matching indexed reference is required; mixed builds require the existing validated SNP lift and chain.

Output lives at `Profiles/<stable ID>/BestDataset/Versions/<date_build_run>/`. `BestDataset/current.json` points to the active generation, displayed first in the source view. Earlier versions remain traceable; failed generation retains the previous selection. Outputs in the job and profile version directory use hard links on the same filesystem where supported, with verified-copy fallback.

Core exports are observed-SNP VCF, TXT, TSV and GZIP equivalents, `variant_provenance.tsv`, exclusions, contribution tables and a checksummed manifest. Primary source percentages total 100% of retained SNPs; support percentages overlap. These are attribution counts, not probabilities of correctness or ancestry. The manifest retains all byte-identical aliases and separate provider/version metadata; duplicate bytes never become additional consensus votes. FASTQ/BAM/CRAM and structural data remain source assets, not fabricated derivatives. Existing explicit BCF/PLINK-related workflows can consume compatible core outputs. No perfect, complete or clinically verified genome is promised.

New imports use timestamp, declared version/build and batch identity in provider folders. Original filenames remain in the database. In Move mode, a small `*.dna-source.json` receipt at the previous location records source/profile ID, provider, old name, new name/path, relative target and SHA-256. Receipts are excluded from recursive batch DNA selection. If identical content is already stored, only another provenance record is created and the redundant input removed after verifying the canonical bytes; Copy mode retains the input. Shared content does not erase separate provenance claims.
